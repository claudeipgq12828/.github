<p>家宽线路的问题很少出现在白天。同一台机器、同一个出口，上午测出来九十毫秒，到了晚上九点可能翻一倍，丢包从零跳到百分之三，Claude 的对话页开始转圈，严重时直接退回登录界面。多数人只截一张 ping 图就下结论，其实那张图恰好避开了最差的时段。这篇文章按时间线走一遍：几点取样、每个时间节点记什么字段、掉线之后按什么顺序恢复，给出一套可以重复跑、能和前一天对比的实测流程。</p>

<h2>一、取样窗口为什么要横跨三个时段</h2>
<p>单点测量只能说明那一刻的状态，说明不了线路的承载能力。家宽出口在晚间的拥塞来自同一条光分路下的其他用户，属于典型的共享带宽争抢，白天永远测不出来。比较稳妥的做法是把一天切成三段：白天基线、晚高峰压力段、深夜回落段，三段用同一组目标地址、同一套命令，才有对比价值。</p>
<h3>19:30 之前先取一组基线</h3>
<p>这段时间线路空闲，测出来的数字可以当作这条线的上限。命令建议用 <code>ping -n 100 目标</code>（Windows）或 <code>ping -c 100</code>（Linux/macOS），间隔一秒，记录平均、最大、标准差三个值。基线丢包应当是零，如果白天就有百分之一以上的丢失，问题不在高峰，而在物理链路或上游配置，先解决那一层再谈优化。</p>
<h3>21:00 到 22:30 是压力最集中的九十分钟</h3>
<p>这一段建议每十五分钟跑一轮，一共六轮。每轮除了延迟，还要单独记一次 TCP 握手耗时，用 <code>curl -o /dev/null -s -w "%{time_connect} %{time_total}\n" https://目标域名</code> 就能拿到。握手时间比 ICMP 延迟更能反映真实体验，因为 ICMP 常被中间设备降优先级处理，数字好看但页面照样卡。</p>

<h2>二、四个时间节点各记录哪些字段</h2>
<p>实测最容易犯的错是记录不统一：今天记平均延迟，明天记最大值，两份数据放一起没法比。建议固定四个节点，每个节点固定字段，写进同一张表，一周之后趋势自然浮出来。</p>
<h3>拨号或重连后的头两分钟</h3>
<p>这两分钟属于收敛期，路由可能还在切换，测出来的数字偏高是正常的，不要拿来当结论。真正要记的是「第几次探测开始稳定」，一般三十秒到九十秒之间。如果超过三分钟还在抖动，说明上游线路本身有问题，换时段重测也没有意义。</p>
<h3>会话建立之后的稳定期</h3>
<p>稳定期要记的是持续性和中断次数，而不是单个延迟数字。可以用一个每十秒发一次请求的小脚本跑满两小时，统计失败次数和最长连续失败时长。后者比失败率更能说明问题：偶发单次失败不影响使用，连续四十秒以上失败基本等同于掉线。</p>

<h2>三、延迟归属用 mtr 分层定位</h2>
<p>延迟高不等于线路差，得先知道高在哪一段。mtr 能把路径上每一跳的延迟和丢包摊开，是最省事的工具，Linux 直接 <code>mtr -rwzc 100 目标地址</code>，Windows 可以用 WinMTR 或 <code>tracert</code> 配合多轮采样。</p>

<h3>从第几跳开始涨，就查那一跳之后</h3>
<p>如果第一跳就一百毫秒以上，问题在本地网关、路由器或光猫；如果前三跳正常、第四跳突然抬高并一直保持，问题多半在运营商骨干或国际出口；如果只有最后一跳显示丢包而前面全绿，通常是目标侧对 ICMP 做了限速，这种情况不必当成故障。判断的关键是看「涨上去之后有没有回落」，一路上涨不回落才是真拥塞。</p>

<h2>四、丢包的三种形态与对应验证</h2>
<p>丢包率是个笼统指标，同样是百分之二，成因可能完全不同，处理方式也相反。先把形态分清楚，再动手改配置，能省掉大量无效折腾。</p>

<h3>末跳丢包但应用完全正常</h3>
<p>这是最容易被误判的一类。ICMP 在很多网络里被当作低优先级流量，路由器 CPU 忙时会直接丢弃探测包，但转发面照常工作。验证方法很简单：同时跑 ping 和一次真实的 HTTPS 请求，如果 ping 有丢包而请求全部成功、耗时稳定，就不用管它。反过来，如果请求也开始超时，那才是真丢包。</p>

<h2>五、掉线之后按固定顺序恢复并计时</h2>
<p>掉线时人的第一反应是重启一切，结果是问题复现不了，也没留下任何线索。更有效的做法是把恢复拆成有顺序的几步，每步计时并记录现象，几次之后就能判断是链路层、会话层还是账号侧的问题。</p>
<h3>恢复顺序与每步的观察点</h3>
<p>建议的顺序是：先看本地网关是否可达，再看出口 IP 是否变化，再看代理端口是否仍在监听，最后才重新登录。前两步各三十秒内能完成，第四步往往要等几十秒的验证码和二次确认。把每步耗时记下来，如果每次都是最后一步慢，说明瓶颈在账号验证而不是网络，再怎么调线路也没用。</p>

<h2>常见问答</h2>
<h3>晚高峰延迟翻倍一定要换线路吗？</h3>
<p>答：不一定。先看翻倍之后是否稳定在某个区间，如果波动小、没有丢包，实际使用感知往往可以接受。只有当峰值延迟伴随持续丢包、握手时间超过两秒，或者频繁触发重新登录时，才值得考虑换出口或换时段。</p>
<h3>ping 通但 Claude 打不开是什么原因？</h3>
<p>答：常见于 DNS 解析异常或 TLS 握手被中断。可以先 <code>nslookup</code> 确认解析结果是否正常，再用 <code>curl -v</code> 看握手停在哪一步。如果能解析但握手超时，问题通常在出口侧的中间设备，与本机设置关系不大。</p>
<h3>连续测几天才有参考价值？</h3>
<p>答：建议至少覆盖三个工作日加一个周末。工作日和周末的峰值时段不同，只测一天很容易把偶发维护当成常态。四天数据放在一起，看每天同一时段的数值是否收敛，收敛了才说明规律稳定。</p>
<h3>无线连接能不能用来做这类实测？</h3>
<p>答：可以做初筛，但不适合定论。无线链路的抖动本身就有几十毫秒，会盖住线路的真实差异。要判断出口质量，还是用网线直连，并且关掉同网段的其他大流量设备。</p>
